# Phase 4 — 核心升级与兼容性验收

## 目标

在 A3 已合并版本的基础上，重新验证一台全新 Ubuntu 24.04 VPS 的安装、健康检查、备份和回滚流程，并把 sing-box 核心的稳定版解析、升级和回滚流程固定为可重复验证的维护能力。完成后更新文档、提交 GitHub，并只在证据完整时发布。

## 工作步骤

1. **本地基线与安全边界**
   - 确认工作树、分支和远端边界，保留 A3 已合并内容。
   - 运行 shell 语法检查、本地测试和 secret 扫描；不把 VPS 密码、UUID、私钥、WARP 密钥或节点链接写入仓库。

2. **新 VPS 的 A3 回归**
   - 使用已下载的仓库脚本完成全新安装，确认核心、配置、systemd 服务、健康定时器、权限和防火墙状态。
   - 先创建显式备份，再执行健康检查、配置错误注入、服务恢复和回滚；输出仅保留脱敏状态、哈希和退出码。

3. **官方稳定版解析与核心矩阵**
   - 以 sing-box 官方 GitHub Releases API 为当前来源，排除 draft/prerelease 后按语义版本选择稳定版，并记录 API 返回的 tag、资产名和 SHA-256。
   - 对照 `sb.sh` 的安装、升级、资产校验和旧版兼容路径；若仍依赖 HTML/JsDelivr 的 latest 正则，改为可验证的官方 API/资产流程，并补充离线单元测试。

4. **A4 VPS 升级与回滚验收**
   - 在 VPS 上备份核心、配置、systemd 单元、健康检查脚本和 release marker 后升级目标核心。
   - 分别校验 `sb.json`、`sb11.json` 和 `sb10.json` 的语法/兼容性，确认服务重启、健康定时器和端口监听结果。
   - 注入受控失败，验证升级失败时可恢复旧核心和旧配置；任何失败都保留可读的脱敏报告，不直接覆盖用户数据。

5. **真实客户端路径验收**
   - 在不保存订阅密钥或节点链接的前提下，使用可用的实际客户端路径做至少一次连接/握手验证。
   - 若本轮没有可用客户端凭据，只报告服务器侧证据为通过，并明确客户端侧未验证，不把“服务 active”当作完整验收。

6. **文档、测试与发布**
   - 更新 README、迁移/发布说明、A4 验收报告和变更记录，写清稳定版来源、支持矩阵、回滚命令、风险与未验证项。
   - 运行完整测试、`git diff --check`、fresh-clone 检查和最终 secret 扫描；确认工作树干净后提交、推送、创建并合并 PR，必要时创建带校验和的 release tag。

## 完成标准

- A3 回归和 A4 核心升级/回滚均有退出码、版本、配置哈希和服务状态证据。
- 核心下载只接受官方稳定版本并通过资产 SHA-256 校验；旧版配置兼容性结论有实际检查依据。
- 仓库没有凭据、私钥、UUID、WARP 密钥、订阅链接或临时日志。
- GitHub 上的合并提交、文档和发布物可复核；未完成的客户端验证明确标注。
